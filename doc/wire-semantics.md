# Wire semantics

The SDK sends JSON through one transport pipeline. These rules describe values that reach Commerce, independent of the TypeScript model names.

## Values in requests

For JSON bodies, `undefined` object properties are omitted by `JSON.stringify`; `null` is transmitted as JSON `null`. A missing `body` sends no JSON body. This applies to PATCH too: omit a property to leave it unspecified; send `null` only when that endpoint's PATCH contract permits clearing it. `undefined` array elements serialize as `null`, so omit an array property rather than placing `undefined` inside an array.

The serializer preserves `false`, `0`, empty arrays, and empty strings. Individual server fields may still reject an empty value. Query parameters omit `undefined`, retain `false` and `0`, and reject `null`. Numeric query values must be safe integers; `limit` must be positive and `offset` nonnegative.

Before sending an ordinary JSON body, transport rejects non-finite numbers, integers outside JavaScript's safe range, `BigInt`, invalid `Date` objects, and cyclic objects. It also scans the final serialized bytes, so a custom `toJSON()` cannot introduce an unsafe number or silently remove the body; serializer failures become generic `CommerceValidationError` messages. The exact `serializedBody` escape hatch preserves signed bytes but still requires valid JSON syntax and safe numeric literals. A valid `Date` in a JSON body becomes an ISO-8601 string through `Date.prototype.toJSON()`. Server timestamps are represented as ISO-8601 strings at the JSON boundary; call `toDate(value)` to convert a valid timestamp to a `Date` explicitly.

Go `int64` money amounts, usage totals, and counters can exceed JavaScript's exact integer range. Outbound ordinary JSON values must be safe integers (`Number.isSafeInteger`); no `BigInt` is sent. Inbound JSON is scanned **before** `JSON.parse`, and an integer outside the safe range raises `CommerceProtocolError` rather than returning a rounded value. The SDK does not silently switch these fields to strings.

## Responses

Endpoints choose a response kind. `data` requires a `{ data: ... }` envelope and returns its value. `list` requires an array `data` and nonnegative safe-integer `total`, returning the whole `{ data, total }` page; `{ data: null, total: 0 }` normalizes to an empty array. Direct responses have no `kind` and return parsed JSON as-is. `raw` returns the `Response` for streaming; `none` discards the body and returns `undefined`. HTTP 202 with JSON decodes normally. HTTP 202/204 with `none` returns `undefined`; an empty 200/204 where `data` is expected is a protocol error, never a typed resource. Except for `raw` and `none`, a successful response must have a JSON content type and valid, size-limited JSON. Malformed envelopes, unsafe numbers, unexpected content types, and redirects raise `CommerceProtocolError`.

Non-success HTTP responses raise `CommerceApiError` with status, code, message, optional details, and `X-Request-ID` when present. After GET retries are exhausted, the final 429/502/503/504 response supplies these fields. Error bodies are read to at most 4096 bytes, then parsed if possible; an oversized or non-JSON body yields the fallback code `http_<status>` and message `HTTP <status>`. Raw error bodies are not attached to errors. Credential echoes and secret-named detail fields are redacted. License validation and online offline-certificate verification explicitly accept HTTP 422 and decode `{ valid: false, ... }` as domain results.

Returned JSON objects keep their secret fields available for explicit property access. `JSON.stringify` and Node's default `util.inspect` render secret-named fields as `[REDACTED]`; use explicit property access when forwarding a one-time API key or certificate. Inspecting a Client or WebhookVerifier also omits configured credentials. Treat custom serializers and object spreads as sensitive: they can still access the original values.

## Retry, timeout, and abort

Only GET requests retry automatically, for 429/502/503/504 or fetch failures, up to `maxRetries` (default 2). `retryOther5xx: true` also retries other HTTP 5xx responses for safe GETs. `retryable: false` disables a GET retry; setting it to `true` cannot enable mutation retries. Multipart requests are never retried. Retry delay uses bounded exponential backoff with configurable `backoffMultiplier` (default 2) and `jitter` (`full` by default, `equal`, or `none`) unless `Retry-After` supplies seconds or an HTTP date; that delay is capped at 30 seconds. The configured timeout is one deadline covering credential resolution, rate-limit waits, fetches, response reads, and retry backoff. The caller's `AbortSignal` cancels all of those stages. A caller cancellation raises `CommerceAbortError`; the deadline raises `CommerceTimeoutError`. For a `raw` response, timeout ends after response headers, while the caller's signal stays connected during body streaming.

The optional local token bucket belongs to one Client instance. Its burst and refill rate are configured by `rateLimit`; waiting attempts take tokens in FIFO arrival order, including retries. `rateLimit.maxQueue` defaults to 1,000 waiting calls; when full, the next caller receives `CommerceLocalRateLimitError` without sending a request. Zero allows only immediately available burst tokens. A cancelled waiter releases its turn without letting later requests overtake an active waiter. Backoff and rate acquisition are separate, but a bucket refilled during backoff adds no extra wait. `rateLimit.clock` can inject `now` and cancellable `sleep` for deterministic tests. The server applies its own independent limits. An exhausted server 429 is `CommerceRateLimitError`, which also passes `instanceof CommerceApiError`.

Dynamic path IDs are percent-encoded as individual segments. Fetch runs with `redirect: 'manual'`, so credentials are never forwarded by an automatic redirect.

## Identification and observability

In Node, Bun, Deno, and workerd, the transport sends `User-Agent: niyantra-commerce-ts/<version> (<runtime>)`. Browser requests omit it and add no replacement identification header. The version constant in `src/utils.ts` is checked against `package.json` by a test.

`ClientOptions.hooks` is opt-in. `onRequest` runs immediately before each fetch, after serialization, signing, authentication, and the local rate wait. `onResponse` runs once after headers arrive, including responses that will be retried or returned as raw streams. `onRetry` runs before backoff for a retryable HTTP status or network failure. Each callback receives a frozen metadata snapshot with the method, collection-level URL path, attempt number (starting at 1), elapsed milliseconds, and request ID when available; response events add status and retry events add reason and delay. Dynamic path segments, query values, headers, bodies, and credentials are never attached. A response header's `X-Request-ID` takes precedence over the caller-supplied request ID.

Callbacks are invoked synchronously and must be fast. Their returned promises are not awaited; callback throws and rejections are swallowed. Hooks cannot alter the request, signed bytes, retry policy, or response. With no hooks, the SDK emits no diagnostics.

`debug: true` mirrors these frozen, redacted events to `logger.debug`; the default logger is a no-op. Middleware registered with `client.use` receives only the method and collection path, and must pass the same frozen request object once to `next`. It may observe or replace the returned result, so middleware failures are caller-visible. Per-call custom headers are merged after authentication, but protected auth, signature, content, routing, request-ID, and idempotency names are rejected before fetch. The server has no general `Idempotency-Key` contract, so the SDK does not generate one.
